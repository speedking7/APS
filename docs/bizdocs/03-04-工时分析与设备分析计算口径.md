# 03-04 工时分析与设备分析计算口径

## 1. 文档目的

本文用于固化 APS 当前“工时分析”和“设备分析”的计算口径，明确：

- 当前前端页面实际展示逻辑；
- 当前后端接口已提供的聚合口径；
- 本轮后端对齐的目标边界；
- 已知口径缺口和后续收敛方向。

本文是 2026-05-25 交接文档的正式化版本，供后续开发、联调、测试和验收统一引用。

## 2. 数据来源与通用约束

### 2.1 主数据来源

- 生产计划结果：`t_production_plan`
- 稼动天数：`t_operating_days`
- 设备台账：`t_equipment_catalog`

### 2.2 通用字段说明

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `planQty` | 生产计划结果 | 计划生产数量 |
| `staffCount` | 生产计划结果/BOM 展开结果 | 持台人数 |
| `taktTime` | 生产计划结果/BOM 展开结果 | 单件节拍，单位秒 |
| `cycleTime` | 生产计划结果/BOM 展开结果 | 制造周期，单位秒 |
| `moldCavity` | 生产计划结果/BOM 展开结果 | 模腔数/取数 |
| `process` | 生产计划结果 | 工序 |
| `equipment` | 生产计划结果 | 设备编码/设备小类匹配键 |
| `manufacturingDepartment` | 生产计划结果 | 制造部门 |
| `manufacturingUnit` | 生产计划结果 | 制造单元 |
| `yearMonth` | 生产计划结果/稼动天数 | 期间，格式 `YYYYMM` |
| `workDays` | 稼动天数 | 当月工作日 |
| `equipmentCategory` | 设备台账 | 设备大类 |
| `equipmentBrand` | 设备台账 | 设备品牌 |
| `equipmentModel` | 设备台账 | 设备小类 |
| `equipmentCount` | 设备台账 | 台数 |

### 2.3 每天有效工时

- 前端页面当前把“每天有效工时”保存在浏览器 `localStorage`：
  - key: `aps.dailyEffectiveHours`
  - 默认值：`10.5`
- 该值当前**没有后端持久化来源**。
- 因此本轮后端口径只能与默认值 `10.5` 对齐，无法感知用户在浏览器里临时改动后的值。

## 3. 工时分析口径

## 3.1 当前页面展示口径

页面：`aps-system/src/main/resources/static/10-workforce-report.html`

当前页面不是调用 `/api/workforce-report`，而是直接读取：

- `/api/production-plan/versions`
- `/api/production-plan/by-version/{version}`

页面当前按“生产计划明细逐行展开”展示，主要字段包括：

- `manufacturingDepartment`
- `manufacturingUnit`
- `itemProjectName / finishedProjectName`
- `itemProductName / finishedProductName`
- `itemProductNo / finishedProductNo`
- `itemCode`
- `yearMonth`
- `planQty`
- `process`

页面当前展示列“所需工时”的实现表达式为：

`requiredHours = (planQty × staffCount × taktTime) ÷ 3600`

说明：

- `taktTime` 单位为秒；
- 页面当前展示值单位为小时；
- 当前前后端已对齐到小时口径。

## 3.2 当前后端聚合口径

接口：`/api/workforce-report`

当前后端 `WorkforceReportService` 的公式为：

`workforceDemand = Σ(planQty × staffCount)`

聚合维度为：

`process + equipment + yearMonth`

过滤规则：

- `process` 为空时跳过；
- `planQty` 为空时跳过；
- `staffCount` 为空或 `0` 时跳过。

当前该接口主要服务于：

- 工作台等聚合视图；
- 既有“人员需求/工时需求”简表逻辑。

## 3.3 本轮工时分析结论

本轮不把 `/api/workforce-report` 直接改造成页面明细接口，原因如下：

- 当前工时分析页已经直接消费 `ProductionPlanView` 明细；
- 仪表盘等旧调用方仍依赖 `/api/workforce-report` 的聚合口径；
- 若强行统一，会同时引入接口语义变化和调用方改造，超出本轮范围。

因此本轮对工时分析的处理边界调整为：

- **保留旧聚合接口**：`GET /api/workforce-report`
- **新增明细接口**：`GET /api/workforce-report/details?version={version}`

新明细接口当前严格镜像 `10-workforce-report.html` 的字段与公式：

- 数据来源：`ProductionPlanService.findViewsByVersion(version)`
- 字段：
  - `manufacturingDepartment`
  - `manufacturingUnit`
  - `project`
  - `productName`
  - `productNo`
  - `productCode`
  - `yearMonth`
  - `planQty`
  - `process`
  - `requiredHours`
- 公式：
  - `requiredHours = (planQty × staffCount × taktTime) ÷ 3600`
- 排序：
  - `yearMonth`
  - `manufacturingDepartment`
  - `manufacturingUnit`
  - `productCode`
  - `process`

后续若要正式统一，建议新增独立接口，例如：

- 一个“工时分析明细接口”对齐页面；
- 一个“工时分析聚合接口”保留仪表盘/汇总口径。

## 4. 设备分析口径

## 4.1 当前页面确认口径

页面：`aps-system/src/main/resources/static/11-equipment-load.html`

页面当前直接读取：

- `/api/equipment-load?version={version}`

设备台账匹配规则为：

`manufacturingDepartment + equipment`

其中：

- `productionPlan.manufacturingDepartment` 对应设备台账 `manufacturingDepartment`
- `productionPlan.equipment` 对应设备台账 `equipmentModel`

命中设备台账时：

- `设备名称（大类） = equipmentCategory`
- `设备品牌 = equipmentBrand`
- `设备型号（小类） = equipmentModel`
- `台数 = equipmentCount`

未命中设备台账时：

- `设备名称（大类） = process`
- `设备品牌 = "—"`
- `设备型号（小类） = equipment`
- `台数 = 1`

## 4.2 当前页面计算公式

当前页面不再在浏览器端重复计算，直接消费后端 `/api/equipment-load` 的计算结果。其确认口径如下：

`requiredSeconds = (planQty × cycleTime) ÷ moldCavity`

其中：

- 当 `moldCavity` 为空、0 或非法时，按 `1` 处理；
- `cycleTime` 单位为秒。

对每个月份：

`availableSeconds = workDays × dailyEffectiveHours × 3600`

对每个聚合分组：

`requiredMachineCount = Σ(requiredSeconds ÷ availableSeconds)`

`loadRate = requiredMachineCount ÷ equipmentCount`

`difference = equipmentCount - requiredMachineCount`

## 4.3 页面聚合维度

当前页面聚合键为：

`manufacturingDepartment + equipmentCategory + equipmentModel + yearMonth`

说明：

- 命中设备台账后，同一制造部门、同一设备小类、同一月份的数据会合并；
- 未命中设备台账时，设备大类回退到 `process`，所以不同工序仍可能拆成不同分析行。

## 4.4 本轮后端对齐目标

本轮 `EquipmentLoadService` 以后端接口 `/api/equipment-load` 为承载，对齐到以下口径：

- 任务量改用 `cycleTime / moldCavity`，不再用旧的 `taktTime`
- 台账匹配规则改为 `manufacturingDepartment + equipmentModel`
- 输出提供页面分析所需字段：
  - `manufacturingDepartment`
  - `equipmentCategory`
  - `equipmentBrand`
  - `equipmentModel`
  - `equipmentCount`
  - `yearMonth`
  - `workDays`
  - `requiredMachineCount`
  - `difference`
  - `loadRate`
  - `matchedCatalog`
- 同时保留兼容字段，支持旧调用方：
  - `equipment`
  - `process`
  - `taskTimeHours`
  - `availableTimeHours`
  - `utilizationRate`
  - `status`
- 支持 `version` 查询参数，供设备分析页按版本直接读取

兼容字段映射规则：

- `taskTimeHours = Σ(requiredSeconds) ÷ 3600`
- `availableTimeHours = workDays × 10.5`
- `utilizationRate = loadRate`
- `status` 仍按负荷率区间计算：
  - `< 50%` → `LOOSE`
  - `50% ~ <85%` → `NORMAL`
  - `85% ~ <100%` → `TIGHT`
  - `>=100%` → `OVERLOADED`

## 4.5 本轮已知缺口

后端无法读取浏览器 `localStorage` 中的 `dailyEffectiveHours`，因此：

- 前端页面如果用户保持默认值 `10.5`，则前后端口径一致；
- 前端页面如果用户手动修改了每天有效工时，页面结果会与后端 `/api/equipment-load` 产生偏差。

这不是公式错误，而是配置存储位置尚未统一。

后续收敛建议：

1. 将“每天有效工时”改为后端持久化配置；
2. 页面和后端统一读取同一配置源；
3. 再把设备分析页切换为直接消费 `/api/equipment-load`。

## 5. 本轮实施边界总结

- 工时分析：
  - 先完成正式口径文档；
  - 暂不改变 `/api/workforce-report` 接口语义。
- 设备分析：
  - 使用 TDD 改造 `EquipmentLoadService`；
  - 补设备台账命中/未命中的回归测试；
  - 保留兼容字段，避免影响现有仪表盘调用。
